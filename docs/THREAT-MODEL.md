# Threat model

## What blackout is defending against

- **Attention extraction.** The product shows sponsored toasts and pays a
  fraction of a cent per view. Blackout answers the inventory call with nothing
  and acknowledges receipts without claiming them, so no ad is shown and no
  impression is claimed.
- **Surveillance through ad targeting.** The tagger sends a small vocabulary of
  language ids and file basenames. Blackout never forwards `serve` at all, so
  even that never leaves the machine.
- **Being broken by an app update.** The interception point is a documented
  environment variable and three path names, not a patched bundle.

## What it is not defending against

- **A build that ignores `ADCODE_AD_SERVER`.** If a future ADCode hard-codes its
  ad origin, this design cannot intercept it. The honest response is a new rule
  or a fork, not a claim that the blocker still works.
- **Ads rendered from the app bundle.** Sponsored UI shipped inside the asar is
  invisible to a network proxy.
- **A hostile local process.** The proxy trusts anything that can connect to
  loopback. On a single-user desktop that is the normal trust boundary; on a
  shared host, run it in your own session and do not expose the port.
- **Malicious updates to blackout itself.** Installing from source and reading
  the diff is the mitigation. There is no signed binary release yet.
- **A compromised upstream.** Blackout never trusts the config: it forces
  `killSwitch: true` and `dailyCap: 0`, and constructs the exact key set the
  client validates. A hostile response cannot widen caps, because the caps it
  can send only tighten locally.
- **Traffic analysis of pass-through calls.** Auth, AI and update checks still
  go to the real server and are not hidden.

## Assets and boundaries

| Asset | Where it lives | Who can read it |
| --- | --- | --- |
| Journal of decisions | `~/.local/state/blackout/journal.jsonl` | the user |
| Policy | `~/.config/blackout/config.json` | the user |
| Recorded AppImage path | `~/.config/blackout/appimage` | the user |
| Launcher | `~/.local/bin/adcode` | the user |
| Ad responses | memory only | nobody |

No credentials are stored by blackout. The proxy forwards the client's own
`Authorization` header to the upstream for config; it does not cache it, log it,
or write it to disk.

## Control-plane protection

`POST /pause` and `POST /resume` require an `x-blackout-control` header. A
browser cannot set a custom header cross-origin without a CORS preflight, and
the proxy answers no CORS preflight. That blocks the trivial
`<form action="http://127.0.0.1:8790/_blackout/pause">` attack from a web page.
It does not stop a local process, which is out of scope.

`/dashboard` sends `Content-Security-Policy: default-src 'none'` with inline
style and script only, and loads nothing remote.

## Logging

The journal records: rule id, path, receipt count and up to 32 receipt ids,
config status, upstream errors, and discovered ad-like endpoints. It does not
record request bodies, tags, filenames, tokens or creative content. Receipt ids
are opaque random ids generated by the client.

## Residual risk

- A future release may add a new ad endpoint that is neither in the rules nor
  matched by the discovery pattern; `report` would under-count until a rule is
  added.
- A local attacker can stop the proxy or rewrite the journal. The chain only
  makes the rewrite visible.
- Loopback is not a security boundary against other users on the same machine.
